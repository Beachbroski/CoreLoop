**Status: HOLD AT `full`.** Not a sign-off. This is the instrument for re-checking.

## 1. What this gates, and the verdict

`docs/platform-split/08-release-qa-sunset.md:9` (W8-1) defines this document: *"Enumerate every capability of today's creator web dashboard … verify each exists in the app or is explicitly descoped with a written reason. This checklist — not vibes — is the sunset gate."* `08-release-qa-sunset.md:33` (W8-12) makes it one of three conditions for flipping the flag, alongside ≥60% of monthly-active creators signed into the app and no open CRITICAL app bugs. The flip itself is staged — `full` → `readonly` → `sunset` (W8-13, `08-release-qa-sunset.md:34`) — driven by `CREATOR_WEB_MODE` (`lib/creator-web-mode.ts:17`).

**Verdict: hold at `full`.** The app is not in the App Store and cannot currently be built, so no creator can reach the replacement surface at all — every downstream W8-12 condition (60% app sign-in, no CRITICAL bugs) is unmeasurable by construction, and 21 capabilities creator web has today have no app equivalent, with 22 more only partly covered. Even setting the build problem aside, six of the gaps are load-bearing rather than cosmetic: **there is no replacement surface at all for a creator who is not on an iPhone** — `mobile/android/` does not exist, `mobile/eas.json:33-41` defines one store profile, and `app/get-the-app/page.tsx:92-93` states Android "is not scheduled" (X-01), so creator web *is* the product for those creators and sunset removes it with nothing behind it; **an accepted creator loses the brief they are contractually delivering against** the moment its deadline passes (D-26); **the entire Earnings tab — lifetime hero, every payout row, the empty state — is replaced by a “Connect payout account” prompt whenever `stripeOnboarded` is false** (E-01), and that flag is recomputed on every Stripe `account.updated` (`app/api/webhooks/stripe/route.ts:212-223`), so a verification failure hides a creator's payment history exactly when they need it; payout history is capped at 20 rows on the app with no way to page (`mobile/src/app/(app)/earnings/index.tsx:165-195` — no `onEndReached`, no `fetchNextPage` caller) while web is unpaginated (`app/(dashboard)/creator/payouts/page.tsx:21-33`); push — the app's only notification channel — cannot be delivered by any build that exists (`mobile/src/lib/push.ts:77-88` returns `unconfigured`); and admin "view as creator", the sole support tool for "a creator says X is broken", dies at `sunset` with no replacement on either surface (`lib/view-as.ts:32-36`, no `/api/v1` admin scope).

**This document is not a one-time sign-off.** It is written ahead of the gate it governs. Re-run it — re-reading each cited line, because both columns move — before each of the three flag flips. §6 says what must be true before each one.

**Reading rules used here.** Every row cites `path:line` on both sides or names the absence. A capability is Parity only if a creator can *reach a screen* that does it — an implemented hook with no caller is not a capability (`mobile/src/lib/queries/use-update-me.ts:21` is the standing example: fully written, referenced only by its own test). Where a survey and the code disagreed, the code won.

## 2. The parity table

**135 capabilities.** Parity 56 · Partial 22 · Missing 28 (17 outright, 11 awaiting a decision) · Descoped 12 · App-only 17. Paths are relative to the repo root.

Of the 28 Missing, **21 are things creator web does today and the app cannot** — those are the gate. The other seven (N-05, N-08, AU-14, X-02, X-03, X-05, X-07) are absent on both surfaces and are listed because they change what a creator experiences once the app is their only surface.

Status vocabulary, used strictly:
- **Parity** — the app does it fully, via a screen a creator can reach.
- **Partial** — the app does some of it; the row says exactly what is missing.
- **Missing** — the app cannot do it.
- **Descoped** — deliberately not coming, with the written reason and its citation.
- **App-only** — the app has it and creator web never did.
