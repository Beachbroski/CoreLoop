## 1. What this is and how to use it

This is a factual map of every piece of personal data the CreatorDocks platform touches: what it is, where it lives, why it is collected, who can see it, which vendors it reaches, how long it stays, and what happens to it when someone asks to be deleted. It is derived from reading the code, not from what any existing document claims. Three audiences share it: whoever rewrites `app/privacy/page.tsx` (start at §8, then §2 and §3), whoever fills the DPA annexes for a brand customer (§2, §3, §5), and an engineer building export or erasure (§2, §5, §6, §7). Every claim carries a `path:line` citation. **This is a data map, not legal advice** — no legal conclusion here is authoritative; classifications and "basis" notes are engineering observations to be reviewed by counsel before anything from this document is asserted to a user, a customer, or a regulator.

## 2. Master inventory

### 2.0 How to read the tables

**Classification key** — an engineering label, not a legal determination:

| Code | Meaning |
|---|---|
| **DI** | Direct identifier — names or contacts a person on its own |
| **II** | Indirect identifier — identifies in combination, or is an attribute of an identified person |
| **PS** | Pseudonymous — identifies a person only via a join inside this database |
| **SC** | Special-category *risk* — unconstrained free text a person authored or authored about them; can contain Art. 9 content the schema never asked for |
| **NP** | Non-personal on its own |

**Four standing facts that apply to every row and are not repeated:**

1. **There is no automated retention anywhere.** No `vercel.json`, no `app/api/cron/*` (verified 2026-09-07 — both `ls` calls return "No such file or directory"), no TTL, no retention constant. *One correction to an earlier draft: the grep `retention|expiresAt|ttl` over `app/`, `lib/`, `prisma/`, `mobile/src/` does **not** return zero. Re-run, it returns incidental substring matches — `settles`, `scrollEventThrottle`, a `Blue Bottle` test fixture, and case-insensitively the privacy page's own "Retention and security" heading (`app/privacy/page.tsx:20`). Do not re-cite that grep; the conclusion below is what is reproducible.* The only `delete`/`deleteMany` calls in the codebase are four, all user- or event-triggered: `app/api/v1/applications/[id]/route.ts:47`, `app/api/v1/devices/[token]/route.ts:16`, `app/api/_lib/account-deletion.ts:53`, `lib/push.ts:60`. **"Indefinite" below means exactly that.**
2. **"Account deletion" is anonymization of the `User` row plus deletion of `Device` rows — nothing else.** `anonymizedUserFields()` rewrites seven columns and `anonymizeAccount()` runs both writes in one transaction (`app/api/_lib/account-deletion.ts:30-56`). `Application`, `Submission`, `Payout`, `Campaign` and `WaitlistSubmission` are never touched.
3. **One database serves local dev, Vercel Preview and Production.** `docs/runbooks/migrate.md:3-9` ("There is exactly one Neon Postgres database… no per-environment database isolation yet"), `docs/PROJECT-STATE.md:122`. A developer laptop with `DATABASE_URL` reads live personal data. Compounding it: `lib/prisma.ts:13` enables Prisma `['query','error','warn']` logging whenever `NODE_ENV !== 'production'`, and query logs carry bound parameter values — so any non-production deployment against the shared database writes real emails and names into its runtime logs. **Do not describe environments as segregated in a DPA.**
4. **Admin sees everything — through two different gates, and they are not the same gate.** `isAllowedAdminUser` requires **both** the `role === 'ADMIN'` column **and** membership of the `ADMIN_ALLOWED_EMAILS` env allowlist (`lib/admin-config.ts:29-31`; allowlist read at `:14`; note `:23` — an *empty* allowlist returns true whenever `NODE_ENV === 'development'`). That two-part gate protects the `/internal` pages: `app/internal/users/page.tsx:11,59-62,80-82` (every BRAND/CREATOR user's name, email and activity counts), `app/internal/waitlist/page.tsx:36` (the whole waitlist on screen) and `app/internal/waitlist/export/route.ts:18-21,23-75` (the whole waitlist as CSV). **Admin "view as" is gated on the `role` column alone**: `lib/view-as.ts:30,32-38` tests `actingUser.role === 'ADMIN'` and never imports `isAllowedAdminUser` or `isAdminEmailAllowed`, so a `User` row carrying `role = ADMIN` can read any brand's or creator's dashboard — pitches, submissions, review notes, payout rows, brand metrics, settings, plus the subject's own name and email — **even if its address is not in `ADMIN_ALLOWED_EMAILS`**, and nothing records that it happened. See §7 G29. **Do not tell a DPA author that the allowlist is the whole answer to "who has access".**

**Column shorthand:** *Subject* = the person the data is about · *Counterparty* = the brand or creator on the other side of a deal · *Admin* = a `role = ADMIN` row, **plus** the `ADMIN_ALLOWED_EMAILS` allowlist for the `/internal` pages but **not** for view-as (standing fact 4) · *Server-only* = never leaves the server to any client — a claim this revision had to withdraw from four rows, so treat it as load-bearing wherever it still appears.

## 4. Collection points and transmission

Two structural facts frame all of it:

- **Two front doors, one database.** The Next.js web app (brand + admin + public waitlist) authenticates with Clerk **cookies** and enforces an origin check on every mutating route (`lib/request-security.ts:32-62`). ### 4.4 Four log exposures the code creates without any `console.*` call

1. **The Expo push token is a URL path segment** — `DELETE /api/v1/devices/{token}` (`mobile/src/lib/push.ts:124`; `app/api/v1/devices/[token]/route.ts:9`). Vercel's platform access logs record request URLs regardless of what our handlers log, so a device identifier is written to a log store on every sign-out. Moving it to a request body closes this.
2. **IP addresses reach Upstash on nearly every request** as part of the rate-limit key. Highest-frequency egress of an online identifier in the system, and invisible in the current policy.
3. **`?viewAs=<userId>` is a query parameter on twelve dashboard routes**, so an internal `User.id` — and, by inference, which admin read which subject's dashboard — is written to Vercel platform access logs by exactly the mechanism point 1 describes, and appears on pages where `<Analytics />` is mounted (`app/layout.tsx:46-58`). Links are built at `app/internal/users/page.tsx:64,85` and consumed at `app/(dashboard)/brand/page.tsx:193`, `creator/page.tsx:194`, `brand/metrics/page.tsx:61`, `brand/applications/page.tsx:102`, `brand/submissions/page.tsx:116`, `brand/settings/page.tsx:76`, `brand/campaigns/[id]/page.tsx:234`, `brand/campaigns/[id]/applications/page.tsx:174`, `creator/applications/page.tsx:153`, `creator/payouts/page.tsx:146`, `creator/campaigns/page.tsx:228`, `creator/settings/page.tsx:121`. Combined with the absence of any audit log (§2.4), the access logs are the *only* trace impersonation leaves anywhere — and they were never written for that purpose. §7 G32.
4. **The referral code travels as a query parameter.** `/waitlist?ref=<code>` is read at `app/waitlist/WaitlistForm.tsx:86`, built into the emailed link at `app/api/waitlist/route.ts:55-64` and rebuilt for the admin dashboard at `app/internal/waitlist/page.tsx:18-27,62`. This document treats the code as a credential (§2.3) and notes it often contains a fragment of the person's name or email (G27), so it reaching Vercel access logs and Analytics on every referred visit is material. **Mitigation worth recording alongside it:** `Referrer-Policy: strict-origin-when-cross-origin` (`next.config.ts:26`) keeps it out of cross-origin `Referer` headers — but not out of our own logs.

### 5.1 Retention

Anonymization is not only a policy choice today — a hard delete would fail with a foreign-key error unless the dependents are handled first.

### 5.3 What survives an account deletion

**Erased (creator):** the Clerk identity and every session; `name`, `avatarUrl`, `bio` → null; `email` → `deleted-<id>@deleted.creatordocks.invalid`; `clerkId` → `deleted-<id>`; `stripeAccountId` → null; `stripeOnboarded` → false; **all** `Device` rows.

**Retained:** the `User` row itself plus `role`, `createdAt`, `updatedAt`; every `Application` (pitch, rate, `paymentIntentId`); every `Submission` (contentUrl, caption, notes, the brand's reviewNote); every `Payout` (amount, fee, `stripeTransferId`); every `Campaign` if the subject was a brand; **the uploaded media files themselves**; the Stripe Connect account; Resend's copies of past emails; Neon backups and branches; Vercel logs and analytics.

**One visible consequence of retaining `role`:** the admin users list filters `role: { in: ['BRAND','CREATOR'] }` (`app/internal/users/page.tsx:14`) and `role` is never scrubbed, so **an anonymized creator keeps appearing on that internal list forever** — as `deleted-<id>@deleted.creatordocks.invalid`, with their retained application count beside it (`:17,82`). Anyone answering "what does a deleted account look like to staff?" needs this sentence.

**The stated basis** is "a financial and contractual audit trail the brand side still needs" (`account-deletion.ts:12-14`, echoed at `app/api/v1/me/route.ts:79-83`). That is a coherent position for amounts and identifiers. It is a *weaker* fit for a pitch, a caption and a set of notes, which are the creator's own prose kept verbatim — a narrower scrub would keep the ledger intact. **That is a decision to make deliberately, not by default** (§7 G8). Legal sufficiency of the basis is outside this document's scope.

**In-app copy vs behaviour.** The first dialog says name, photo and login are removed, sessions end immediately, and "Campaign, application, submission, and payout records are kept in anonymized form for financial record-keeping" (`mobile/src/app/(app)/profile/index.tsx:93`); the second says there is no way to sign back in (`:102`). Both match the code. **Neither mentions that uploaded photos and videos are kept**, and "anonymized" overstates it — `User.id` survives and joins everything back together, so this is pseudonymization (§7 G9).
